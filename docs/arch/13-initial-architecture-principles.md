# 初始版本的可扩展性与契约原则

## 目的

初始版本不应只追求“当前功能可以跑通”。当系统已有明确的能力边界时，应优先固定稳定的协作契约，把容易变化的产品语义、存储方式和具体实现留给调用方或后续模块装配。

这一原则服务于 Seele 作为无产品语义 runtime 的定位：框架提供执行原语与扩展接口；Seelex 等上层决定任务、工作区、持久化、计费和用户体验。

## 1. 先定义接口，再收敛具体实现

在识别出一项能力的稳定输入、输出和生命周期后，应先在使用方定义最小接口，再实现默认实现或适配器。例如：

- `workplan` 依赖最小的 `Node`，不依赖 Agent、Task 或产品 DSL。
- `event` 定义 `Sink` 与 `Locator`，不依赖 EventStore、Task 或日志产品。
- `tools` 定义 Function Calling 与分发契约，环境相关工具由上层注册。

接口应描述已经稳定的能力，而不是预先枚举所有猜想的字段。默认实现只能是接口的一个实现；调用方可以在后续用自己的 struct、adapter 或 provider 细化装配。

```text
稳定的执行契约  →  最小 interface  →  默认实现 / 调用方实现
                                               ↓
                                  后续按产品语义装配具体 struct
```

这样保留扩展空间，但避免为了“以后也许会用到”而引入空泛的上帝接口、全局注册表或循环依赖。

## 2. 统一错误与事件，区分控制流和观察事实

跨模块边界必须有统一的结构化错误与事件形式：

- `errors.Error` 用于控制流：返回、包装、定位、`errors.Is`/`errors.As`。
- `event.Event` 用于观察事实：ID、时间、状态、Scope、内容引用、位置和安全的 `Failure` 投影。

两者不能相互替代。事件记录失败不得覆盖业务错误；事件里的 `Failure` 不能携带敏感的 Raw 数据或实现 Cause。统一格式让日志、追踪、审计和状态投影拥有稳定输入，同时仍允许模块通过 `Attributes` 与 `Locator` 附加自己的信息。

日志扩展不应靠不断向根结构体添加产品字段，而应遵循：

```text
通用查询键     → Event.Scope
模块资源地址   → module-owned Locator
小型可检索标签 → Event.Attributes
大体积/敏感值  → 调用方存储 + Event.ContentRef
```

这既保持事件可索引、可序列化，也让 Agent、WorkPlan、Tools 或产品层在不改动框架核心的前提下扩展信息。

## 3. 回调也应有明确契约与所有权

可插拔能力常以 callback 形式出现，但应提升为小型 interface，以承载实现、组合和错误语义。例如 `event.Sink` 的本质是事件回调，仍通过 `Append(ctx, Event) error` 固定调用方向。

- Seele 在自己的运行时边界调用接口。
- 上层实现并注入接口，决定持久化、队列、批处理、重试和投影。
- 框架只处理它拥有的通用语义，例如事件正规化、顺序、取消和错误隔离。

接口调用权属于框架；业务语义与外部资源所有权属于实现方。该划分避免框架反向依赖 Seelex，同时避免上层复制运行时生命周期逻辑。

## 4. 模块 README 是代码边界的一部分

每个 Go package 和有多个 package 的模块目录必须维护邻近 README。README 至少说明：

1. 职责与明确不负责的事项；
2. 公开入口和最小使用方式；
3. 关键数据流、并发/生命周期或序列化约束；
4. 依赖方向与协作模块；
5. 可执行的验证命令。

跨模块且长期稳定的决策写入 `docs/arch/`；单个 package 的 API 细节留在相邻 README；一次性迁移和评审记录归档到 `docs/history/`。完整规范见 [`../DOCUMENTATION_STANDARD.md`](../DOCUMENTATION_STANDARD.md)。

## 5. 实施检查表

新增一项基础能力前，先回答：

1. 它的最小稳定输入、输出和生命周期是什么？
2. 哪些字段属于框架通用关联键，哪些属于模块或产品语义？
3. 谁调用接口、谁实现接口、谁拥有外部资源？
4. 错误是控制流错误、事件事实，还是二者都需要？
5. 默认实现是否可被替换，而不迫使上层依赖框架内部 struct？
6. 新 package 的 README、父模块索引和跨模块架构文档是否已同步？

只有边界已知但具体产品细节尚未稳定时，才优先提供接口和装配点。若能力本身仍不清楚，应先实现小而封闭的具体功能并用测试验证，再提取真实出现的共同契约。
