# Seele 文档标准

> 本文件是仓库唯一的文档规范（single source of truth）。任何人或自动化工具在创建、移动或实质修改 Markdown 文档前，必须先完整阅读本文件。

## 1. 目标与原则

文档应与代码的模块边界一致，使读者从一个目录进入时能回答四个问题：这个模块做什么、如何使用、如何实现、与谁协作。文档不是代码注释的副本，也不应把单个包的说明堆积到集中式 `docs/`。

- **就近**：模块知识与模块源码同目录。
- **分层**：项目、领域子系统、Go package、跨模块主题各有唯一归属。
- **可验证**：描述基于当前代码、测试和配置；链接使用相对路径。
- **可维护**：职责、公开 API、关键实现改变时，文档同一变更同步更新。

## 2. 写作前的必经流程

1. 阅读本标准，并确认变更是“模块说明”“跨模块设计”“过程记录”还是“可运行示例”。
2. 确认影响的模块边界：先用 `go list ./...` 或目录结构识别 package，再阅读目标模块源码和现有 README。
3. 按第 4 节选择唯一落盘位置；不确定时，放在最小能完整解释该行为的模块目录。
4. 使用第 5 节模板写作，必要时补充父级模块的导航链接。
5. 校验事实、相对链接、标题层级与术语；代码与文档必须在同一个改动中提交。

## 3. 模块分层

| 层级 | 定义 | 文档职责 |
| --- | --- | --- |
| 项目根 | 整个仓库 | `README.md` 介绍定位、快速开始、总体架构和顶级索引 |
| 领域模块 | 一组协作包，如 `agent/`、`workplan/`、`seelectx/` | `README.md` 说明子系统职责、主调用路径和子模块导航 |
| 子系统组 | 没有独立 Go package 但包含多个包的目录，如 `agent/core/`、`workplan/runtime/` | `README.md` 说明内部切分和依赖方向 |
| 叶子 package | 一个可构建 Go package | `README.md` 说明功能、公开入口、实现细节、边界和测试 |
| 命令或示例 | `cmd/<name>/`、`example_Implement/<name>/` | `README.md` 说明运行方法、场景、代码路径和预期结果 |
| 跨模块主题 | 多个模块共同的架构决策或长期设计 | `docs/` 下按主题归档 |
| 过程记录 | 一次任务的计划、评审、测试报告、迁移记录 | `docs/history/YYYY-MM-DD-<topic>/` |

所有含 Go 源码的 package 目录都必须有 README；非叶子源码目录也必须有导航 README。`test/` 与仅构建标签启用的工具包同样属于 package，应说明测试范围或构建方式。

## 4. 放置规则

| 内容 | 正确位置 | 不应放置在 |
| --- | --- | --- |
| `ChatClient` 的 API、SSE 状态机、账户选择 | `agent/core/api/README.md` | 根 README、`docs/arch/` |
| WorkPlan 节点与运行顺序 | `workplan/README.md` 及相应子包 README | 单独的临时设计文档 |
| 一个新增模块的目录导航 | 该模块目录 `README.md` | 其他模块的 README |
| 跨 `agent`、`engine`、`seelectx` 的架构决策 | `docs/arch/` | 任一单包 README |
| 版本迁移或一次性实现计划 | `docs/history/YYYY-MM-DD-<topic>/` | 模块 README |
| 可以直接运行的使用场景 | 对应 example 目录 `README.md` | `docs/` 的说明页 |

决策顺序：若内容能由一个 package 的代码完整验证，写在该 package README；若解释多个 package 的稳定协作关系，写在最近的共同父模块 README；若涉及多个领域模块，写在 `docs/`；一次性过程记录与历史决策归档到 `docs/history/`。

**日期归档约束**：任何名称以 `YYYY-MM-DD` 开头的文档文件或目录，均视为历史产物，必须直接放在 `docs/history/` 下；不得留在 `docs/` 根目录、`docs/plan/` 或任何模块源码目录。迁移时保持文件名和目录内结构不变。

## 5. README 内容标准

### 5.1 领域模块与子系统组

必须包含：

1. 一句话职责与边界。
2. 子模块分工表或调用路径。
3. 关键依赖方向/并发或资源生命周期（若适用）。
4. 指向每个子模块 README 的相对链接。

### 5.2 叶子 package

必须包含：

1. `# <目录或 package 名>` 标题。
2. **功能与边界**：它解决什么问题、明确不负责什么。
3. **公开入口**：核心类型、接口、构造函数或命令；不需要罗列所有私有符号。
4. **实现细节**：数据流、策略/适配器、状态管理、并发控制、序列化或错误处理中的关键机制；至少两条与代码相符的说明。
5. **依赖与协作**：上游、下游或相关模块的相对链接。
6. **验证**：对应测试文件、测试包或可执行验证命令。

推荐骨架：

```markdown
# package-name

一句话说明职责与不负责的事项。

## 公开入口

| 符号 | 用途 |
| --- | --- |
| `New...` | ... |

## 实现细节

- ...
- ...

## 依赖与验证

- 协作模块：`../<other>/README.md`
- 验证：`go test ./path/...`
```

### 5.3 命令与示例

必须包含运行命令、前置配置、展示的 API/场景、预期输出或行为；不得把密钥、账户或真实服务地址写入文档。

## 6. 写作规则

- 使用与仓库主文档一致的中文；代码符号、包路径、命令和配置键使用反引号。
- 标题从 `#` 开始，层级不得跳级；表格只用于映射、比较或索引。
- 实现细节描述机制和约束，例如“用 `RWMutex` 保护索引并以 O(1) 查找分发”，而不是笼统写“支持并发”。
- 所有跨文件引用使用相对 Markdown 链接，链接目标优先指向 README 或源文件。
- 不复制大段源码、陈旧计划或测试输出；长期有效的信息才进入 README。
- 通过不确定时，不臆测实现；先查源码或在文档中标记待确认项。

## 7. 同步更新触发条件

发生下列任一情况，必须更新受影响模块 README，必要时更新父级导航或 `docs/`：

- 新增、删除、移动 Go package 或示例。
- 改变公开 API、配置项、数据格式、错误语义或默认值。
- 改变模块职责、依赖方向、协议策略、并发/缓存/持久化行为。
- 新增 Provider、工具类型、WorkPlan 节点或可观测性事件。
- 迁移或废弃跨模块架构方案。

## 8. 完成检查

- [ ] 已先阅读本标准，并选择了正确文档层级。
- [ ] 每个受影响 package 与父模块都有正确 README/导航。
- [ ] README 含功能、公开入口、实现细节、协作关系和验证信息。
- [ ] 新增链接均为有效相对路径，未泄露敏感配置。
- [ ] 文档事实与当前源码、测试和配置一致。
- [ ] 跨模块设计保留在 `docs/`；带日期的过程记录位于 `docs/history/`。

## 9. 标准本身的维护

本标准改变模块层级、落盘规则或必填内容时，应在同一改动中更新 [DOCUMENTATION.md](../DOCUMENTATION.md)、[docs/README.md](README.md) 和相关根 README 索引。
